# Scaffold frontend project

## Summary

Scaffold `frontend/` as a Vite + Vue 3 + TypeScript project: Vue Router with
three placeholder routes (People, Expenses, Balances) wrapped in a shared
app shell (sidebar / bottom tab bar) styled per `_docs/design-system.md`,
Tailwind wired up, MSW installed and wired for dev and test with an empty
handler set, and the `openapi-typescript` / `openapi-fetch` codegen
pipeline configured against `openapi/openapi.yaml`. This is pure tooling
and layout — no feature logic (forms, lists, API calls) is part of this
issue. Issues #4, #5, and #7 build the actual People, Expenses, and
Balances screens on top of it.

## Scope

**Not dependent on `openapi/openapi.yaml` existing** (see "Open questions"
for why this split matters):

1. A Vite + Vue 3 + TypeScript project at `frontend/` (e.g. scaffolded from
   the `vue-ts` Vite template), managed with npm per
   `_docs/architecture.md`.
2. Tailwind CSS wired up: `tailwind.config.*` extends `fontFamily.sans` to
   lead with `'IBM Plex Sans'`, and the IBM Plex Sans Google Fonts
   stylesheet is loaded globally (e.g. from `index.html`) — per
   `_docs/design-system.md`'s Typography section. No color palette
   extension is needed; the design system maps to stock Tailwind classes.
3. Vue Router with exactly three top-level routes — `/people`, `/expenses`,
   `/balances` — plus a redirect from `/` to `/people`.
4. Placeholder view components, one per route (e.g.
   `src/views/PeopleView.vue`, `ExpensesView.vue`, `BalancesView.vue`),
   each rendering only a top-level `<h1>` with the screen's name — no
   lists, forms, or network calls. These are intentionally empty; issues
   #4, #5, #7 replace their contents.
5. An app-shell layout, present on every route, per `_docs/design-system.md`'s
   "App shell", "Sidebar nav item", "Logomark", and "Bottom tab bar"
   sections:
   - Desktop/tablet (`md:` and up): fixed 220px white sidebar with the
     "Tally" logomark and three nav items (People, Expenses, Balances),
     each with the icon named in `_docs/design-system.md`'s Icons section.
   - Mobile (below `md:`): the sidebar is replaced by a fixed bottom tab
     bar with the same three destinations, per the same doc's Responsive
     behavior section.
   - The active route's nav item gets the active styling
     (`bg-indigo-50 text-indigo-700`, 600 weight); the other two stay
     inactive (`text-slate-600`/`text-slate-500`, 500 weight).
6. MSW installed and wired, with no endpoint-specific handlers yet:
   - `frontend/src/mocks/browser.ts` sets up an MSW `setupWorker`, started
     only in dev mode (e.g. gated on `import.meta.env.DEV`) from the app's
     entry point.
   - `frontend/src/mocks/server.ts` sets up an MSW `setupServer`,
     started/reset/stopped around the Vitest suite via a setup file wired
     into `vitest.config.ts`.
   - `frontend/src/mocks/handlers.ts` exports an empty `handlers` array.
     Real handlers land with whichever feature issue first needs one, and
     must be written against the generated contract types (see item 8),
     not a hand-rolled shape.
   - `frontend/public/mockServiceWorker.js` is generated via
     `npx msw init frontend/public --save` and committed, with
     `package.json`'s `msw.workerDirectory` pointing at `public`.
7. Vitest + `@testing-library/vue` configured (per
   `_docs/testing-guidelines.md`'s "Vitest + Vue Testing Library"), plus:
   - `frontend/tests/` directory for cross-component tests (per
     `_docs/architecture.md`'s repository layout).
   - At least one test proving the app shell renders all three nav items
     and that navigating between routes updates the active-item styling
     (satisfies criterion 6 below).
   - At least one cross-component test in `frontend/tests/` exercising
     router navigation end-to-end (satisfies criterion 9 below).
8. `npm` scripts in `frontend/package.json`: `dev`, `build`, `test`, and
   `generate:api-types` (invokes `openapi-typescript` against
   `../openapi/openapi.yaml`, writing to `frontend/src/api/schema.d.ts`).
   The script must exist and be correctly wired regardless of whether
   `openapi/openapi.yaml` exists yet — only *running* it requires the
   contract file (see next group).
9. `frontend/.gitignore` excludes `node_modules/` and `dist/` (but not
   `public/mockServiceWorker.js`, which must be committed per item 6).

**Dependent on `openapi/openapi.yaml` existing** (issue #1 merged — see
"Open questions"):

10. `frontend/src/api/schema.d.ts`, generated by running
    `npm run generate:api-types` against the real `openapi/openapi.yaml`,
    containing a `paths` type.
11. `frontend/src/api/client.ts`, exporting a default `openapi-fetch`
    client instance created as `createClient<paths>(...)`, importing
    `paths` from `./schema.d.ts`.

## Out of scope

- Building the actual People, Expenses, or Balances feature UI (forms,
  lists, data fetching, edit/delete interactions) — issues #4, #5, #7.
- Writing any endpoint-specific MSW handler — the first real handler lands
  with whichever of #4/#5/#7 needs it first, built against generated
  types.
- Wiring the frontend to a real backend — issue #15.
- Backend project setup — issue #8.
- End-to-end/Playwright setup (`e2e/`) — issue #16; a separate project
  entirely, not part of `frontend/`.
- CI wiring for running `npm run build`/`npm test` on push — flagged as an
  open, undecided question in `_docs/architecture.md`, not part of this
  issue.
- Linting/formatting tooling (ESLint/Prettier) beyond whatever the Vite
  `vue-ts` template scaffolds by default — not requested by the issue or
  `_docs/architecture.md`. File a follow-up issue if wanted.
- Deployment/production hosting config (e.g. history-mode fallback
  rewrites for a static host) — deployment target is an explicit open
  question in `_docs/architecture.md`, not decided yet.
- Empty, error, and loading states for the People/Expenses/Balances
  screens — explicitly listed under "What's not covered yet" in
  `_docs/design-system.md`; deferred to whichever feature issue needs
  them.

## Acceptance criteria

1. `frontend/package.json` exists, declaring `vue`, `vue-router`, and
   `openapi-fetch` as dependencies, and `vite`, `typescript`,
   `openapi-typescript`, `tailwindcss`, `postcss`, `autoprefixer`, `msw`,
   `vitest`, and `@testing-library/vue` as devDependencies. No other
   dependency is added without separate sign-off, per `AGENTS.md`.
2. `cd frontend && npm install && npm run build` completes with exit code
   0 and produces a `frontend/dist/` directory.
3. `frontend/src/router/index.ts` (or equivalent) defines exactly three
   top-level routes — `/people`, `/expenses`, `/balances` — plus a
   redirect from `/` to `/people`, and no other routes.
4. `PeopleView.vue`, `ExpensesView.vue`, and `BalancesView.vue` each exist
   under `frontend/src/views/` and each renders only a top-level `<h1>`
   containing the screen's name ("People", "Expenses", "Balances") — no
   other markup, form, list, or network call.
5. The app shell renders, on every route, both a sidebar element (visible
   via `md:`-and-up Tailwind classes, e.g. `hidden md:flex`) and a bottom
   tab bar element (visible via below-`md:` classes, e.g. `md:hidden`),
   each containing exactly three nav items labeled People, Expenses,
   Balances with the icons named in `_docs/design-system.md`'s Icons
   section — checkable by inspecting the rendered markup and class list.
6. A Vitest test (co-located with the app-shell component, e.g.
   `AppShell.test.ts`) mounts the app at each of the three routes in turn
   and asserts: the current route's nav item has the active classes
   (`bg-indigo-50`, `text-indigo-700`) and the other two have the inactive
   classes (`text-slate-600` in the sidebar / `text-slate-500` in the tab
   bar).
7. `frontend/tailwind.config.*` extends `theme.fontFamily.sans` to lead
   with `'IBM Plex Sans'`, and the rendered `index.html` loads the IBM
   Plex Sans Google Fonts stylesheet.
8. `frontend/src/mocks/browser.ts`, `frontend/src/mocks/server.ts`, and
   `frontend/src/mocks/handlers.ts` all exist; `handlers.ts` exports an
   empty array; the dev entry point starts the MSW worker only when
   `import.meta.env.DEV` is true; a Vitest setup file (referenced from
   `vitest.config.ts`) starts the MSW server before the suite and resets
   handlers between tests. `frontend/public/mockServiceWorker.js` exists
   and is tracked (not gitignored).
9. `frontend/tests/` contains at least one test that navigates between all
   three routes (via the router, not by reloading the page) and asserts
   the corresponding placeholder `<h1>` renders each time.
10. `cd frontend && npm test` runs the full Vitest suite and every test
    passes, including the tests from criteria 6 and 9.
11. `frontend/package.json` defines a `generate:api-types` script that
    invokes `openapi-typescript ../openapi/openapi.yaml -o src/api/schema.d.ts`
    (or an equivalent invocation with the same input/output paths). This
    criterion is checkable — the script exists and is correctly wired —
    regardless of whether `openapi/openapi.yaml` exists yet.
12. **If `openapi/openapi.yaml` exists in the repo at implementation time**
    (i.e. issue #1 has been merged): running
    `cd frontend && npm run generate:api-types` exits 0 and produces
    `frontend/src/api/schema.d.ts` containing a `paths` type; and
    `frontend/src/api/client.ts` exports a default `openapi-fetch` client
    created as `createClient<paths>(...)`, importing `paths` from
    `./schema.d.ts`; `npm run build` (which type-checks) still passes
    with this file in the source tree.
13. **If `openapi/openapi.yaml` does not exist yet at implementation
    time**: criterion 12 is not attempted. `frontend/src/api/schema.d.ts`
    and `frontend/src/api/client.ts` are not created against a fabricated
    or placeholder contract; the gap is flagged back on this issue (e.g. a
    comment noting the issue is blocked on #1) rather than worked around.
14. `frontend/.gitignore` excludes `node_modules/` and `dist/`, and does
    not exclude `frontend/public/mockServiceWorker.js`.

## Edge cases considered

- **`openapi/openapi.yaml` not existing yet**: this is the central risk
  for this issue — see criteria 11–13 and "Open questions". The tooling,
  routing, and app-shell work (criteria 1–10) is fully independent of the
  contract's existence and should be completed regardless.
- **Responsive behavior in tests**: Vitest/JSDOM doesn't evaluate real
  viewport width or CSS media queries, so criterion 5 is verified by
  inspecting which Tailwind responsive utility classes are present in the
  rendered markup (both the sidebar and tab bar are always in the DOM;
  CSS controls which one is visible at a given width), not by simulating
  an actual narrow viewport.
- **Sidebar/tab-bar mutual exclusivity**: the two must use exactly
  opposite breakpoint classes (e.g. `hidden md:flex` and `flex md:hidden`)
  so they never both render visibly at the same width, per
  `_docs/design-system.md`'s Responsive behavior table.
- **MSW handlers starting empty**: safe because no view in this issue
  makes a network call yet (the placeholder views render static text
  only) — there's nothing for a handler to intercept until #4/#5/#7 add
  one.
- **Test co-location vs. `frontend/tests/`**: per
  `_docs/testing-guidelines.md`, the app-shell's own unit test is
  co-located next to it; the router-navigation test that spans the shell
  and all three placeholder views goes in `frontend/tests/` since it
  crosses more than one component.
- **`openapi-typescript`/`openapi-fetch` version compatibility**: must
  support OpenAPI 3.0.3 input (the version fixed by
  `specs/groomed/1-define-openapi-contract.md`); avoid picking a package
  major version that assumes 3.1-only input.

## Constraints

- Package manager is npm, not yarn or pnpm, per `_docs/architecture.md`'s
  repository layout.
- No dependency beyond the list in acceptance criterion 1 is added to
  `frontend/package.json` without asking first, per `AGENTS.md`. The list
  in criterion 1 is itself pre-approved via `_docs/architecture.md`, which
  already names every one of these tools.
- Vue components use `<script setup lang="ts">` throughout, per
  `_docs/architecture.md`.
- Styling is Tailwind utility classes only, matching
  `_docs/design-system.md`; no CSS-in-JS and no hand-written arbitrary
  values beyond the roundings that doc already calls acceptable.
- The frontend never hand-declares types for API request/response shapes
  once the generated schema exists — that's the entire point of the
  codegen step (criteria 10–12); this issue must not introduce a
  hand-typed interface as a stand-in.

## Open questions

- **Hard sequencing dependency on issue #1**: `openapi/openapi.yaml` does
  not exist in this repo yet (issue #1 is groomed but not implemented).
  Per `specs/features/expense-splitter-poc.md`'s build order, the frontend
  phase is meant to start only once the contract phase closes, so this
  spec assumes issue #1 lands (the file exists at that exact path) before
  criteria 12 (codegen + typed client) are attempted. Criteria 1–11 and 13
  don't depend on it and can proceed regardless. If a human instead wants
  the typed-client work to start in parallel against a throwaway/
  placeholder contract, that's a deviation from the documented phase
  ordering and needs explicit sign-off — this spec does not assume that.
- **Default landing route**: assumed `/` redirects to `/people` (no
  existing doc records this decision). Trivial to change to `/expenses` or
  `/balances` if a different first screen is preferred.
- **`openapi-typescript`/`openapi-fetch` exact versions**: assumed latest
  stable release of each, compatible with OpenAPI 3.0.3 input; no specific
  version is pinned anywhere else in the repo. Flag if a specific version
  is required for compatibility with a later toolchain decision.
- **`@testing-library/vue` vs. `@vue/test-utils`**:
  `_docs/testing-guidelines.md` says "Vitest + Vue Testing Library," so
  this spec assumes `@testing-library/vue` (which itself depends on
  `@vue/test-utils` under the hood). Flag if bare `@vue/test-utils` was
  actually intended instead.
