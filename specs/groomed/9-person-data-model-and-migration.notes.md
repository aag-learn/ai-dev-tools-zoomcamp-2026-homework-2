# Implementation notes: #9 Person data model and migration

## Open questions resolution

- **Test file location**: the spec's own text defaults to a flat
  `backend/tests/test_person_model.py`, but flagged that #10 will soon add
  a sibling `test_expense_model.py`. The human maintainer explicitly
  decided (per the task brief) to use a `models/` subdirectory instead, so
  this implementation places the test at
  `backend/tests/models/test_person_model.py`. No `__init__.py` or extra
  `conftest.py` was added under `tests/models/` — pytest's rootdir-based
  discovery finds tests in subdirectories without package markers, and the
  `db_session`/`client` fixtures defined in `backend/tests/conftest.py`
  apply automatically to any subdirectory, confirmed by running the full
  suite (`uv run pytest -v`) and seeing both new tests collected and
  passing alongside #8's existing tests.

- **Autogenerate vs. hand-written migration**: used
  `uv run alembic revision --autogenerate -m "create people table"`
  against a throwaway SQLite file. Alembic correctly detected the new
  `people` table and generated `op.create_table(...)` (not
  `op.batch_alter_table(...)`, since creating a new table needs no
  `ALTER TABLE`) — matching criterion 9 without hand-editing. The
  generated file's boilerplate autogenerate comments
  (`# ### commands auto generated by Alembic - please adjust! ###`) were
  left as-is since they're Alembic's standard template output and don't
  affect behavior.

## What was built

- `backend/src/app/models/person.py` — `Person` SQLAlchemy model,
  `__tablename__ = "people"`, `id` (Integer, PK, autoincrement) and `name`
  (String(100), nullable=False). Matches the spec's scope item 1 exactly.
- `backend/src/app/models/__init__.py` — now imports and re-exports
  `Person` (`from app.models.person import Person`, `__all__ =
  ["Person"]`), replacing the empty placeholder from #8.
- `backend/alembic/env.py` — added `import app.models  # noqa: F401 -
  registers models on Base.metadata` right after the existing `from
  app.db.base import Base` import and before `target_metadata =
  Base.metadata` is set, so `Base.metadata` includes the `people` table
  during autogenerate/upgrade/downgrade.
- `backend/alembic/versions/36f11f583866_create_people_table.py` — the
  first migration, `down_revision = None`. `upgrade()` calls
  `op.create_table("people", ...)` with an `id` integer primary key
  (autoincrement) and a `name` `VARCHAR(100) NOT NULL` column;
  `downgrade()` calls `op.drop_table("people")`.
- `backend/tests/models/test_person_model.py` — two tests using the
  `db_session` fixture from `backend/tests/conftest.py`:
  - `test_insert_persists_with_auto_assigned_id_and_name` — inserts
    `Person(name="Alice")`, commits, re-fetches via `db_session.get`, and
    asserts the id is auto-assigned and non-null and `name == "Alice"`.
  - `test_duplicate_names_both_persist` — inserts two `Person(name="Bob")`
    rows, commits, and asserts both persist with distinct auto-assigned
    ids (no uniqueness constraint violation).

No other files were touched. `backend/tests/conftest.py` was not modified
— the `db_session` fixture's `Base.metadata.create_all(...)` picks up the
`people` table because pytest imports all test modules (including the new
`test_person_model.py`, which does `from app.models import Person`) during
collection, before any fixture runs; this registers `Person`'s table on
the shared `Base.metadata` in time for every test's fixture setup, so no
extra import wiring is needed in the fixture file itself.

## Manual verification performed

Run from `backend/`, against a throwaway SQLite file
(`/tmp/test_migrate.db`), matching acceptance criteria 6-8:

- `DATABASE_URL="sqlite:////tmp/test_migrate.db" uv run alembic upgrade
  head` — exit 0; `sqlite3 /tmp/test_migrate.db ".schema people"` showed
  `id INTEGER NOT NULL`, `name VARCHAR(100) NOT NULL`, `PRIMARY KEY (id)`.
- `DATABASE_URL="sqlite:////tmp/test_migrate.db" uv run alembic revision
  --autogenerate -m "check"` immediately after `upgrade head` produced a
  migration whose `upgrade()`/`downgrade()` were both just `pass` —
  confirms `Base.metadata` (via the `app.models` import in `env.py`)
  matches the migration exactly. This check-revision file was deleted
  immediately after and is not part of the commit.
- `DATABASE_URL="sqlite:////tmp/test_migrate.db" uv run alembic downgrade
  base` — exit 0; `sqlite3 /tmp/test_migrate.db ".tables"` afterward
  showed only `alembic_version` (no `people` table).
- `cd backend && uv run pytest -v` — all 9 tests pass (7 pre-existing from
  #8 plus the 2 new ones in `tests/models/test_person_model.py`).

## Assumptions

- No backend linter is configured in this repo yet (`pyproject.toml` has
  no `ruff`/`black`/`flake8` section, and no root-level lint command is
  documented in `AGENTS.md`), so no lint step was run beyond `uv run
  pytest`.
- Interpreted "no other columns, and no relationship() to any other
  model" (criterion 2) literally — `Person` has exactly `id` and `name`,
  no timestamps or other implicit columns.
